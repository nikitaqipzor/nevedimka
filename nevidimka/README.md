# Невидимка — Release 1 + Release 2 + Release 3 + Release 4

Реализация всех четырёх релизов из `docs/PROJECT_SPEC.md` (раздел 20):

- **Release 1** — ядро Telegram-бота: онбординг, День 0, договор с собой,
  главная цель, ежедневный цикл, хранилище идей.
- **Release 2** — Mini App / PWA: «Сегодня», «Путь», «AI-наставник»,
  «Дневник», «Аналитика», «Карта навыков», «Хранилище идей».
- **Release 3** — «Показать результат»: конвейер подготовки и публикации
  текстового поста с обязательным подтверждением.
- **Release 4** — «Собрать историю»: конвейер обработки видео (вырезка пауз,
  вертикальный кроп, нормализация звука, обложка, превью) и публикация.

Критерий приёмки Release 4: видео проходит весь конвейер до preview и
публикуется только после подтверждения; вертикальный формат и вырезки —
настоящие, проверены на реальном видеофайле.

## Структура

```
apps/bot               — Telegram-бот (grammy) + express-сервер под webhook
apps/web                — Mini App / PWA (Next.js): экраны + API-роуты как backend
apps/worker              — фоновый воркер обработки видео (ffmpeg pipeline)
packages/shared-types   — общие TS-типы домена
packages/db              — SQL-миграции, RLS, pg-клиент, repository-слой
packages/ai               — AI-оркестратор ролей (Anthropic API) + промпты
packages/telegram         — общий клиент Telegram Bot API (текст и видео)
packages/video             — ffmpeg-конвейер обработки видео
docs/PROJECT_SPEC.md    — полное ТЗ (источник истины)
```

## Release 1 (бот) и Release 2 (Mini App/PWA)

Без изменений — см. предыдущие версии этого раздела: онбординг, `/today`,
фокус-сессии, отчёты, `/idea`, `/evening`, проактивные напоминания; Mini App
с полным дневным циклом, аналитикой, картой навыков, дневником, чатом с
AI-наставником, PWA-установкой.

## Release 3 (публикация текста)

Без изменений — команда `/post` в боте и «Студия контента» в Mini App:
источник → 3 AI-версии текста → выбор → проверка приватности → финальный
снапшот → явное подтверждение → публикация. Идемпотентность гарантирована
уникальным индексом в БД.

## Release 4 (видео)

Конвейер (PROJECT_SPEC.md раздел 9):

```
Видео от пользователя (бот, команда /video)
        ↓
Проверка формата/длительности (до 180с) — packages/video
        ↓
Извлечение аудио
        ↓
Детекция пауз (ffmpeg silencedetect) → план вырезок
        ↓
Применение вырезок (concat выбранных сегментов)
        ↓
Безопасный вертикальный кроп 9:16 (центрированный)
        ↓
Нормализация громкости (loudnorm) + шумоподавление (afftdn)
        ↓
[Субтитры — только если подключён ASR, см. ограничения ниже]
        ↓
Обложка + Preview (пониженное разрешение/битрейт)
        ↓
Уведомление пользователю в Telegram, что превью готово
        ↓
Явное подтверждение («Подтвердить и опубликовать»)
        ↓
Финальный рендер (apps/worker)
        ↓
Публикация видео в канал (packages/telegram, multipart-загрузка)
```

Обработка видео вынесена в отдельный процесс **`apps/worker`**: он
опрашивает `video_assets` на предмет новых загрузок (`status='uploaded'`) и
подтверждённых черновиков (`status='confirmed'`), прогоняет ffmpeg-конвейер
и сам уведомляет пользователя в Telegram о результате на каждом шаге — бот
и веб только читают/пишут статус в БД, не блокируясь на медленной обработке.

### Что реально работает (проверено на настоящем видео, не только typecheck)

- Детекция пауз и вырезка — без ИИ и без ASR, чисто по аудио-анализу.
- Безопасный вертикальный кроп (центрированный, без claim на трекинг лиц).
- Нормализация громкости и шумоподавление.
- Обложка и превью (пониженное качество для быстрого просмотра).
- Финальный рендер с сохранением кропа/вырезок.
- Публикация видео в канал (multipart-загрузка с обложкой и подписью).
- Идемпотентность публикации — тот же уникальный-индекс подход, что и в
  Release 3, отдельным индексом для видео.
- Мягкие субтitles (soft track, `mov_text`) — код готов и проверен на
  вручную заданной расшифровке.

### Сознательные ограничения Release 4

- **ASR (расшифровка речи) не подключена** — как и в Release 1/2, честно
  задокументированная заглушка (`packages/video/src/asr.ts`). Без неё:
  нет субтитров и нет AI-подсказок по смысловым блокам речи — но вырезка
  пауз, кроп, нормализация, обложка, превью и финальный рендер работают
  полностью, потому что не зависят от расшифровки.
- AI-роль «видеоредактор» (семантический план вырезок по транскрипту) не
  реализована в этом релизе — без ASR ей нечего анализировать; вырезка
  пауз по тишине уже покрывает основной сценарий «убрать дубли и провисания».
- Загрузка видео — только через бота (`/video`). Mini App показывает статус,
  превью и кнопки подтверждения/отмены, но не принимает сам файл — загрузка
  больших файлов через Telegram Mini App требует отдельной инфраструктуры
  вне рамок этого релиза.
- Файлы (оригинал, превью, финал) хранятся локально на диске
  (`VIDEO_STORAGE_ROOT`), без потоковой отдачи (`GET .../file` читает файл
  целиком в память) — нормально для лимита 180 секунд, но не годится для
  production-масштаба без замены на объектное хранилище с поддержкой Range.
- Один канал на инсталляцию, как и в Release 3.

## Установка

Требования: Node.js ≥ 20, Postgres (или Supabase), ffmpeg (с `libx264`,
`libass`, `aac` — стандартная сборка Ubuntu подходит), токен Telegram-бота,
ключ Anthropic API, ID закрытого канала.

```bash
npm install
cp .env.example .env
# заполнить .env — см. комментарии в файле для каждой переменной
```

Применить миграции (001 → 005, идемпотентно):

```bash
npm run db:migrate
```

Откатить последнюю миграцию (или несколько — `npm run db:migrate:down -- 3`):

```bash
npm run db:migrate:down
```

Каждая миграция `packages/db/migrations/00X_*.sql` имеет пару в
`packages/db/migrations/down/00X_*.sql`. Откат проверен полным циклом
(вверх → вниз для всех пяти → вверх снова) на настоящем Postgres.

## Запуск

```bash
npm run dev:bot                              # бот (long polling)
npm run --workspace=apps/web dev             # Mini App / PWA
npm run --workspace=apps/worker dev          # видео-воркер (только если нужна обработка видео)
```

Продакшн-сборка:

```bash
npm run build
node apps/bot/dist/index.js &
node apps/worker/dist/index.js &
PORT=$WEB_PORT node apps/web/.next/standalone/apps/web/server.js
```

`apps/worker` — отдельный долгоживущий процесс; без него загруженные видео
останутся в статусе `uploaded` навсегда (бот и веб не запускают ffmpeg сами).

## Проверка

```bash
npm run typecheck   # tsc --noEmit по всем 8 пакетам/приложениям
npm run build        # полная сборка в правильном порядке зависимостей
```

CI (`.github/workflows/ci.yml`) прогоняет оба шага на каждый push/PR —
`npm ci` → `typecheck` → `build`, проверено локально с абсолютно чистого
состояния (без единого предустановленного `node_modules`/`dist`).

Все точки входа свободного текста (отчёты, идеи, чат с наставником,
онбординг, исходник и финальный текст поста — и в боте, и в Mini App)
проверяют длину через общий `validateTextLength` (`packages/shared-types`)
до того, как текст попадёт в AI-вызов или базу — см. `AUDIT_REPORT.md`.

Помимо typecheck/build, следующее проверено сквозными тестами против
настоящей инфраструктуры (не моков на уровне кода):

- Все 5 миграций применяются идемпотентно к реальному Postgres 16.
- Сквозные сценарии Release 1/2/3 (см. предыдущие версии этого раздела).
- **Release 4**: синтетическое видео (9с, с настоящим 2.5с провалом
  тишины) прогнано через весь `packages/video` конвейер — детекция паузы,
  вырезка (9с → 7.2с), вертикальный кроп (1280×720 → 1080×1920),
  нормализация, обложка, превью, финальный рендер — все выходные файлы
  проверены через `ffprobe`, не просто «код выполнился без ошибки».
  Отдельно проверено вшивание субтитров (soft track `mov_text`).
- **Полный воркер end-to-end**: `processUploadedAsset` и
  `processConfirmedAsset` прогнаны против настоящего Postgres и
  локального мок-сервера Telegram Bot API — включая проверку, что
  `sendVideo` реально отправляет `multipart/form-data` с приложенным
  видеофайлом (проверен размер тела запроса), и что уникальный индекс
  публикаций и уведомления пользователю отрабатывают корректно.
- В процессе тестирования найдена и исправлена настоящая ошибка в
  `packages/telegram` (потерянная строка сборки URL при добавлении
  fallback на `TELEGRAM_API_BASE_URL`), которая сломала бы вообще все
  вызовы Telegram API — обнаружена именно благодаря реальному
  HTTP-тестированию, а не только typecheck.

## Аудит и усиление (после Release 4)

Полный независимый аудит — в `AUDIT_REPORT.md`. Коротко, что было найдено
и исправлено:

- **Критично**: изоляция данных между пользователями (RLS) не работала с
  Release 1 из-за бага в `withUserContext` (`set_config` терял область
  видимости вне явной транзакции) — исправлено, заново проверено настоящей
  атакой «пользователь А пытается прочитать/изменить данные пользователя Б»
  под непривилегированной ролью Postgres.
- **Критично**: у бота не было контроля доступа — `OWNER_TELEGRAM_ID` был
  описан в `.env.example`, но нигде не проверялся. Добавлен гейт в
  `bot.ts`.
- Таймауты на ffmpeg-процессы и Telegram API-вызовы, восстановление
  зависших видео-джобов воркера после падения (`recoverStaleVideoJobs`),
  retry с backoff для AI-вызовов, отслеживание примерной стоимости
  (`ai_logs.cost_usd`) — реализовано и проверено.
- **Лимиты на длину пользовательского текста** (`MAX_TEXT_LENGTH` /
  `validateTextLength` в `packages/shared-types`) подключены во всех точках
  приёма свободного текста в боте и Mini App — проверено реальным HTTP-
  запросом с текстом сверх лимита.
- **Rate limiting на AI-вызовы**: не более `AI_RATE_LIMIT_MAX_CALLS` за
  `AI_RATE_LIMIT_WINDOW_MINUTES` на пользователя, на основе `ai_logs`
  (общий счётчик корректен даже при том, что бот/веб/воркер — разные
  процессы). Проверка встроена прямо в `callRole` — единственную точку,
  через которую проходит любой AI-вызов, так что новую роль в будущем
  невозможно случайно добавить в обход лимита. Проверено реальным тестом:
  подтверждено, что при превышении лимита `callRole` блокирует запрос **до**
  обращения к Anthropic API (мок-сервер получает 0 запросов от
  заблокированного пользователя) — то есть это настоящая защита от
  расходов, а не просто ошибка после того, как деньги уже потрачены.

Ещё не сделано (осознанно, см. `AUDIT_REPORT.md`): LICENSE-файл,
потоковая отдача видео (HTTP Range), Docker/docker-compose, структурное
логирование вместо `console.log`.

## Тестирование (после аудита) и down-миграции

Дальше — на прямой вопрос «есть ли кнопки, или всё через команды» (был
только второй вариант) добавлены `/settings`, регистрация меню команд
Telegram (`setMyCommands`) и постоянная reply-клавиатура. Затем — по
запросу продолжить работу над Mini App и инфраструктурой:

- **Mini App проверен в настоящем headless-браузере** (Playwright,
  Chromium) — не только `next build`, а реальные клики, заполнение форм,
  проверка на необработанные JS-исключения. Это закрыло самый большой
  пробел из `READINESS_SCORECARD.md`.
- **Тесты этой сессии больше не одноразовые** — три набора закоммичены в
  репозиторий и гоняются в CI при каждом push/PR:
  `packages/db/test/rls.test.ts` (атака на изоляцию между пользователями —
  тот самый критический баг, только теперь под постоянной защитой),
  `apps/bot/test/full-flow.test.ts` (9 проверок: весь путь через
  `bot.handleUpdate()`), `apps/web/test/e2e.test.ts` (7 проверок в
  настоящем браузере). CI (`.github/workflows/ci.yml`) поднимает Postgres
  service container и Chromium, гоняет `npm test` после сборки.
- `test/` теперь тоже входит в `npm run typecheck` (раньше не входил —
  `tsx` транспилировал тесты без проверки типов). Это сразу поймало
  реальное несоответствие типов в тестовых фикстурах.
- **Down-миграции**: `packages/db/migrations/down/00X_*.sql`, по одной на
  каждую forward-миграцию. `npm run db:migrate:down [n]` откатывает N
  последних. Проверено полным циклом на настоящем Postgres: применить все
  5 → откатить все 5 по одной → накатить заново → накатить и
  многошагово откатить 3 разом — во всех случаях схема совпадает с
  ожидаемой.

## Инфраструктура и оставшееся тестовое покрытие (по плану улучшения)

- **`Dockerfile` + `docker-compose.yml`** — многоступенчатая сборка на
  npm workspaces, три образа (bot/worker/web) из одного Dockerfile,
  отдельный лёгкий production-слой зависимостей (без TypeScript/tsx/
  Playwright в рантайме). `docker compose up --build` поднимает Postgres,
  прогоняет миграции отдельным шагом, стартует все три сервиса.
  **Честно**: собрать через настоящий `docker build` не удалось — в среде
  разработки не было доступа к Docker-демону. Пути и синтаксис тщательно
  вычитаны и сверены с тем, что реально проверено в этом репозитории
  (структура standalone-сборки Next.js, расположение `migrate.js` и т.д.),
  но первый настоящий `docker compose up` — это и есть первая живая
  проверка.
- **Структурное логирование**: новый пакет `packages/logger` (обёртка над
  `pino`, с редактированием токенов/паролей в выводе). Все 18 мест
  `console.*` в `apps/bot` и `apps/worker` заменены на структурированные
  вызовы с уровнями (`info`/`warn`/`error`/`fatal`) и контекстными полями
  (userId, assetId и т.п.).
- **Тест `packages/video`** (`test/pipeline.test.ts`) и **тест
  down-миграций** (`packages/db/test/migrations.test.ts`) — оба уже
  закоммичены и гоняются в `npm test`/CI: конвейер ffmpeg на настоящем
  синтетическом видео (6 проверок), и полный цикл
  вверх→вниз-все→вверх→многошаговый откат для миграций (3 проверки) —
  включая проверку, что у каждой forward-миграции есть парный down-файл.
- **Видео-экраны Mini App** добавлены в `apps/web/test/e2e.test.ts`:
  список `/studio/video` и деталка с реальным нажатием кнопки
  «Подтвердить и опубликовать», с проверкой, что статус реально
  меняется в БД, а не только на экране.
- **`LICENSE`** — добавлен консервативный дефолт «все права защищены» с
  пояснением, как заменить на MIT/Apache 2.0, если репозиторий когда-нибудь
  станет публичным. Открытый исходный код не предполагался явно, поэтому
  выбор — не отдавать права по умолчанию, а не наоборот.

Итоговый набор тестов после всего этого: **28 проверок** в четырёх
пакетах/приложениях (`packages/db` — 4, `packages/video` — 6, `apps/bot`
— 9, `apps/web` — 9), все закоммичены и гоняются в CI при каждом
push/PR — не одноразовые скрипты.

## Продолжение разработки: экран настроек в Mini App

Аудит фичей показал разрыв паритета: у бота есть `/settings` (часовой
пояс, время напоминаний), а у Mini App — не было вообще. Заодно
обнаружилось, что `listPublications` (история публикаций) и функции
редактирования/удаления уже опубликованного поста в `packages/telegram`
существуют, но нигде не вызываются — честно зафиксировано как известный
пробел, не исправлено в этом заходе.

**Добавлено**: `/settings` в Mini App — `/api/settings` (GET текущих
значений, POST на обновление, та же валидация IANA-таймзоны, что и в
боте) плюс сам экран с переключателями утреннего/вечернего напоминания.
Ссылка — в хабе «Ещё».

Проверено не только компиляцией: реальный браузерный тест заполняет
поле часового пояса, нажимает «Сохранить», проверяет сообщение об
успехе, включает утреннее напоминание через чекбокс, выбирает час,
сохраняет — и напрямую читает БД, чтобы подтвердить, что оба значения
(`Europe/Moscow`, час `7`) реально записались, а не просто показались на
экране. Тестов теперь **29** (в `apps/web` стало 10).

## ASR (расшифровка речи) — реализовано, с честной оговоркой

Раньше — единственный сознательно пропущенный пункт из
`FEATURE_ROADMAP.md` (требовал внешнего провайдера). Реализовано против
OpenAI Whisper API (`POST /v1/audio/transcriptions`, `verbose_json` —
даёт таймкоды по сегментам из коробки).

**Разблокировало сразу три вещи, ничего специально доделывать не
пришлось** — весь конвейер уже был спроектирован их принять:
- Субтитры на опубликованном видео (`packages/video`'s `pipeline.ts` уже
  писал `.srt` и вшивал его, как только транскрипт не `null`).
- Автоматическая расшифровка голосовых/видео-отчётов в боте — вместо
  просьбы напечатать краткое резюме, отчёт сразу уходит на AI-ревью.
- `apps/bot/src/services/asr.ts` не дублирует логику — просто
  переиспользует `packages/video`'s реализацию.

**Важная честная оговорка**: `api.openai.com` не был доступен в среде, где
это писалось (сетевые ограничения песочницы блокируют все домены, кроме
явно разрешённых — включая, для сравнения, `huggingface.co` и
`openaipublic.azureedge.net`, из-за чего локальная модель Whisper тоже
оказалась технически невозможна проверить здесь). Интеграция целиком
проверена через мок-сервер, повторяющий документированный формат
запроса/ответа OpenAI — 4 теста в `packages/video/test/asr.test.ts`
(корректный multipart-запрос, разбор таймкодов, обработка ошибок,
ответ без сегментов), плюс сквозной тест, что весь видео-конвейер
реально генерирует и вшивает субтитры при настроенном ASR
(`packages/video/test/pipeline.test.ts`), плюс 2 теста на обёртку бота.
**Но ни один настоящий HTTP-запрос к `api.openai.com` с настоящим аудио
никогда не был выполнен.** Первая реальная транскрипция после того, как
вы впишете свой `ASR_API_KEY` — это и есть первая настоящая проверка
именно этой интеграции, не что-то уже подтверждённое до конца.

Нужен другой провайдер или self-hosted вариант (whisper.cpp,
faster-whisper — оба реалистичны для личного бота на своём сервере, без
платы за токены)? Единственное место для замены —
`packages/video/src/asr.ts`, одна функция; всё остальное зависит только
от формы `VideoTranscript`, не от того, кто её произвёл.
